# Spec: Read view — a rendered counterpart to the editor

> Status: **settled**
> Created: 2026-09-10
> Grilled: 2026-09-10 — 7 rounds, 32 decisions
> Suggested next: /spec-breakdown

## Goal

Give every vault note two ways to be looked at: the existing CodeMirror **edit view** over raw
markdown, and a new **read view** that renders it — no line numbers, no syntax, prose in
proportional sans, with a header block naming the note and a Read/Edit toggle in the chrome strip.
`doc/v0-spec.md` §5.1 anticipated this from the start ("accepted cost: building preview/toolbar by
hand"); nothing in the app has ever converted markdown to HTML until now.

Source: mockups 6a (dark) / 6b (light).

## Settled Decisions

| # | Decision | Chosen | Rationale |
|---|----------|--------|-----------|
| 1 | Where does the view mode live? | Per-buffer `view: BufferView` on `EditorBuffer`, session-only | Mirrors `vimMode`, which already lives there; two notes open in different modes is the useful case, and a global toggle would change what you're doing when you switch tabs |
| 2 | Which buffers get a read view? | Vault notes only; the toggle is **hidden** for config buffers | TOML has nothing to render, and hide-never-disable is the established rule for an inapplicable control |
| 3 | Which view does a note open into? | **Read** | Chosen against the recommendation of `edit`. Reading is the common case; writing is the deliberate one |
| 4 | What about a note that was just created? | Opens in **edit** | A note created by `startNoteDraft` or the daily note is empty — you made it in order to write in it, so read would mean pressing `Ctrl-w e` every single time |
| 5 | What does the read view render? | The **in-memory buffer**, dirty included | One source of truth, no new read, and toggling becomes an instant preview of what you just typed |
| 6 | Is the inactive view still mounted? | Both mounted, inactive one hidden | The pattern `Viewer` already uses for buffers, applied one level down: scroll position, CodeMirror undo history and cursor all survive a toggle. Swapping would unmount CodeMirror — the exact failure `keymap-compartment.ts` exists to avoid |
| 7 | How is markdown rendered? | `@lezer/markdown` tree walked into React elements | ADR 0125. One parser for both views; no HTML string, so no sanitizer and no injection surface |
| 8 | Raw HTML inside a note? | Rendered as **escaped text**, never executed | What makes the renderer sanitizer-free rather than sanitizer-deferred; an agent writes these notes |
| 9 | Fenced code blocks? | `highlightCode` + the existing `acidantheraHighlightStyle`, at `--font-mono` | Identical palette to the editor for free. Not `settings.editorFont` — a display face chosen for the editor should not reach rendered prose |
| 10 | Images? | **Vault-local only**, via `convertFileSrc`; a remote URL renders its alt text | Keeps a local-first app from making an outbound request because of something an agent wrote into a note |
| 11 | External `https://` links? | Open in the OS browser via `@tauri-apps/plugin-opener` | Already a dependency and already permitted. Underlined and monochrome, so leaving the app looks different from navigating inside it |
| 12 | Typeface for rendered prose? | **Proportional sans** | Sharpens the documented rule rather than breaking it: mono is for *source*, sans is for *rendered prose*. Mono stays for metadata and code |
| 13 | Prose measure? | ~680px, centred in the card | Full-width prose is unreadable at this window size; matches the mockup's ~675px |
| 14 | Heading weight? | Capped at 500 | The mockup draws the title near 700; the design system's weight ceiling is a live rule with no reason to break here |
| 15 | Where does the toggle live? | Right-aligned in the **viewer's chrome strip** | ADR 0123 admits controls that act on what the window is showing, which a view toggle is |
| 16 | What is the toggle made of? | A **monochrome** two-option control, not the current `Segmented` | `Segmented`'s active state is `border-accent bg-accent-soft` — ember, which invariant 21 reserves. A view toggle is not AI agency, and chrome is monochrome unless the control *is* the AI surface |
| 17 | What about `Segmented`'s existing ember? | Add a monochrome variant and move `SettingsDialog`'s theme row to it | That row is a **pre-existing** invariant-21 violation already on screen; closing it here beats widening it |
| 18 | What holds DOM focus in read view? | A `tabIndex={-1}` scroll container, claimed via the existing `editorFocusRequest` nonce | Invariant 20 needs a claimant and there is no CodeMirror. A div is not an editable target, so unlike the editor and the agent dock the window dispatcher **does** see its keys — every global chord works with no region-exit gesture |
| 19 | Does `j`/`k` scroll? | No — native scrolling only | A `viewer` keymap layer would touch `KeymapLayer`, the dispatcher, `keymaps.toml` seeding and the keymap reference. Arrows/Page/Space satisfy §5.5 today |
| 20 | How is the toggle bound? | `global.toggle-view`, default `Ctrl-w e` | The 4th id `executeAppCommand` dispatches and the 9th in `REGION_EXIT_COMMANDS`, so it fires from inside the editor too — the pattern `global.daily-note` set. `editor.*` was rejected: `useCommandChord` returns `undefined` for ids outside `EDITOR_COMMAND_IDS`, so it would render no chord anywhere |
| 21 | What is in the note header block? | Breadcrumb, title, meta line | All three are cheap and truthful with what the app already knows |
| 22 | Tags and `+ tag`? | **Cut entirely** | No tag concept exists anywhere in the app, notes have no frontmatter parsing, and `vault-agents.md` promises "no required frontmatter". Choosing a syntax, writing a parser and writing into the user's notes is its own epic |
| 23 | Where does the title come from? | The filename **stem**; a leading `# H1` in the body is suppressed | The breadcrumb already carries the full basename. Without suppression every well-formed note shows its name twice, six pixels apart |
| 24 | What does the meta line say? | `edited <relative> · N links · N min read` | `modified` and `relativeTime` already exist. `links` counts `[[…]]` only — the app's one link concept that carries meaning — and read time is words ÷ 200, rounded up. Free for the **open** note, which is not what ADR 0114 refused |
| 25 | Is the breadcrumb clickable? | **Inert metadata** | There is no reveal-in-sidebar command in the app; making it clickable means inventing one, with its own focus question |
| 26 | How do wikilinks render? | **Clickable and ember**, in both views | Chosen against the recommendation. Amends ADR 0105, invariant 21, §5.6 and `wikilink.ts`'s own comment — recorded as ADR 0126 so it reads as a decision, not a violation |
| 27 | Does the editor decoration resolve targets? | Yes — it reads the cached vault tree | Forced by 26: if the editor is ember too, it has to know which links are broken, or a bad link looks fine until you toggle |
| 28 | Broken or ambiguous targets? | **Muted + strikethrough**, never ember, never clickable | Ambiguity reuses ADR 0114's stance — two notes sharing a basename means the model cannot express which was meant, so mark it rather than guess |
| 29 | What does the status cluster show? | `N words · N min read`, inside the card, **no `READ` indicator** | The cluster stays where it is. The toggle is the mode indicator, exactly as `CommandBar`'s presence is the global-mode indicator. Refuses the mockup's gutter bar (ADR 0107) and its boxed chip (the deleted `Badge`) |
| 30 | Can the read view write? | Only the task-checkbox toggle | Chosen against a fully read-only recommendation. Clicking `- [ ]` rewrites that line via `updateBufferContent`, marks the buffer dirty, and commits through the existing save loop — no second save path |
| 31 | The ember `✦` in the chrome strip? | **Refused** | ADR 0121 put every global control in the sidebar, ADR 0123 admits only view-scoped ones, and the **Agent** row already exists with its own chord |
| 32 | The mockup's sidebar changes? | **None of them** | `More` row, `synced`, the green status dot and per-row link counts each re-assert a ruling already made. Its `⌘N`/`⌘L` literals are not offerable at all (invariant 31) |

## Explicitly Out of Scope

- **Tags of any kind** — no syntax, no parser, no `+ tag` chip, no tag row. Decision 22.
- **A `viewer` keymap layer** — `j`/`k`/`gg`/`G` scrolling in read view. Decision 19; reversible later.
- **Reveal-in-sidebar** — the command a clickable breadcrumb would need. Decision 25.
- **The mockup's sidebar deltas** — `More`, `synced`, the green status dot, per-row link counts.
  Decision 32.
- **A second Agent entry point in chrome.** Decision 31.
- **Copy-to-clipboard buttons on code blocks** — considered alongside the checkbox write and not taken.
- **Any write from the read view other than the task checkbox.** Decision 30.
- **Footnotes** — outside `@lezer/markdown`'s GFM extension; they render as literal text.
- **Read view for config buffers.** Decision 2.

## Glossary Changes

Added to `.agents/ubiquitous-language.md`:

- *Buffer view* — `BufferView` / `view` on `EditorBuffer`.
- *Read view* — the rendered surface, and the third claimant of viewer DOM focus.
- *Markdown walker* — the `@lezer/markdown` tree → React element renderer.
- *Note header block* — breadcrumb, title, meta line.
- *Wikilink resolution* — stem → path against the cached tree, and the three link states.
- *View toggle* — the chrome strip control.

Sharpened: *Wikilink* (no longer presentation-only, no longer monochrome), *AI accent* and
invariant 21 (ember now also marks a vault link), *Chrome strip* and invariant 23 (a second kind of
view-scoped control), *Editor status cluster* (content varies by buffer view), *Editor buffer*,
*App command*, *Region-exit gesture*, *Design primitive* (`Segmented` gains a monochrome variant),
and invariant 20 (a third focus claimant).

Added: invariants 36 (one parser serves both views), 37 (the read view's only write), 38 (three link
states, identical in both views). The scaffold block's invariants 36–53 renumbered to 39–56.

## Residual Unknowns

- **Footnotes** render as literal text, since `@lezer/markdown`'s GFM extension does not cover them.
  Accepted rather than solved.
- **An existing empty note opened in read view** shows a header block over nothing. Decision 4
  covers a note you *just created*, not one that was already empty. Left as is — the header still
  states the name, the edited time and `0 words`.
- **The exact node coverage of the walker** (definition lists, nested blockquote edge cases) is an
  implementation matter for the plan, not a design decision.
