## How to maintain this document

1. **Add terms** when a new entity, state, or process enters the codebase.
2. **Add aliases to avoid** when ambiguity appears in PRs, chats, or AI-generated code.
3. **Update relationships** when entity connections change (new FK, removed link, etc.).
4. **Flag ambiguities** when a term means different things in different contexts.
5. **Bump "Last updated"** on every edit so AI tools know how fresh the context is.

## Relationships

- `useAppStore.activeRegion` (a `FocusRegion`) is only ever set to `'chat'` while `chatOpen` is `true`, and to `'sidebar'` while `sidebarOpen` is `true`; closing either region reassigns `activeRegion` to `'viewer'` if that region was active. `'viewer'` is unconditionally reachable, so `reachableRegions` never returns an empty list.
- `StatusBar`'s `sidebar` button and the `Ctrl-w` `b` chord (`useGlobalKeymap` and `regionExit` alike) are the only entry points to `useAppStore.toggleSidebar`; `Sidebar` is the sole consumer of `sidebarOpen`, self-guarding with `return null` *after* its hooks (as `ChatPanel` does for `chatOpen`) so the `vault-changed` watcher keeps the tree fresh while hidden.
- `useGlobalKeymap` reads and writes `useAppStore` state exclusively — it holds no state of its own beyond the transient `Ctrl-w` prefix-arm timer.
- `AiFab` is the only UI entry point that calls `useAppStore.toggleChat`; the global keymap's `Ctrl-w c` chord calls the same action, and so does the editor's own `regionExit` chord.
- `Viewer` (`src/components/layout/Viewer.tsx`) is the sole consumer of `useEditorStore`; `regionExit` reads/writes `useAppStore` the same way `useGlobalKeymap` does, but from inside the CM6 extension rather than a `window` listener.
- `read_note`/`write_note` accept a `path` string that must resolve (after canonicalization) inside the current `VaultState` root — in practice this should always be a `path` value previously returned by `read_vault_tree`, since arbitrary strings are rejected by the guard.
- `vaultService.pickVault()` resolves to the chosen folder's path; it does not itself call `useAppStore.setVaultRoot` — that wiring belongs to whichever slice invokes it (`Sidebar`'s "Open vault…" action, #14).
- `create_note`/`create_directory` never touch `useSidebarStore.tree`: creating an entry trips the `notify` watcher, which emits `vault-changed`, which drives `Sidebar`'s existing refetch — so a new note or folder appears through the same watcher path as an externally-created one, with no manual tree invalidation.
- `scaffold_agent_context` runs in both vault-adopt paths (`open_vault` and `pick_vault`), and deliberately *before* `watch` — so the frontend's first `read_vault_tree` already sees the pair and the app's own boot-time writes never emit a `vault-changed`. It is best-effort: a root that cannot be written to (read-only mount, missing permissions) logs a warning and still opens, leaving the agent to run without project instructions.
- Because `useSettingsBootstrap` calls `open_vault` on every boot, `scaffold_agent_context` runs on every boot too. It is idempotent by construction (`create_new` per file), so the user's edits survive and only a deleted file is restored.
- No `AgentBackend` reads the agent-context pair: both engines pick it up themselves from their `cwd` (`useChatStore` passes `useAppStore.vaultRoot` to `AgentBackend.start`). Neither backend may pass a flag that skips project instructions (e.g. Claude Code's `--bare`, doc/v0-spec.md §4.4).
- Because `build_tree` keeps empty directories (#36), a directory created by `create_directory` is visible in the sidebar immediately; it renders as a `FileTreeItem` with `kind="dir"` whose `children` is `[]`, which `flattenVisibleTree` already handles (expanding it simply yields no rows).
- `build_tree` filters `AGENT_CONTEXT_FILES` names only at the vault root (#50) — a nested note that happens to be named `AGENTS.md` (e.g. inside a subdirectory) still renders normally, since only the two scaffolded root files are meant to stay off the sidebar.
- `AgentBackend` implementations are looked up by `AgentSource` through the backend registry (`src/lib/agent/backend-registry.ts`); the chat panel never imports a concrete backend directly — only `AgentEvent` and the registry functions.
- `Sidebar` (`src/components/layout/Sidebar.tsx`) is the sole consumer of `useSidebarStore`; it refetches `vaultService.readVaultTree()` whenever `useAppStore.vaultRoot` changes and whenever `vaultService.onVaultChanged` fires, so the tree stays in sync with the watcher without surgical diffing.
- `openVaultFile` and `useSidebarKeymap` both write `useSidebarStore.cursorPath` and `useEditorStore` (via `openFile`) but never `useSidebarStore.tree` — the tree is owned exclusively by `Sidebar`'s watcher-driven refresh.

- `useSaveLoop` reads `useEditorStore.filePath`/`content` and calls `vaultService.writeNote` directly; it does not go through `Sidebar` or `useSidebarStore`, so saving is independent of the sidebar's own render/mount state.

- `chat-prompt.ts` (#69) imports **type-only** `ChatItem` from `useChatStore` — same "lib depends on a store's types, not its runtime" shape as `chat-file.ts`, no cycle (the store never imports it), erased under `isolatedModules`. It imports **no** backend and never branches on `AgentSource`: `buildResumePrompt` returns a plain string, so which engine consumes it is the caller's concern (the growth-point rule). As of #70 it is **wired** into `useChatStore.sendMessage`: a live same-session turn still sends the raw user text; on the resume boundary (a thread loaded from disk, or a model just switched) the store calls `buildResumePrompt` once with the owned history (`items.slice(0, -1)`) before clearing `pendingResume` — exactly the "first continued turn of a loaded chat" path this module was built for.

## Flagged ambiguities

- **"Vim mode" is two distinct systems** (doc/v0-spec.md §3.4): the app-level `GlobalMode` (`normal`/`command`, app shell slice) and the editor's own CodeMirror vim mode (`EditorVimMode`, editor slice, backed by `@replit/codemirror-vim`). Do not merge these into one enum or one store — they are deliberately separate state machines that only hand off focus at the region boundary.
- **"Adapter" vs `AgentBackend`** (doc/v0-spec.md §4.3): the spec's "adapter" is the per-engine translator (`createClaudeCodeBackend` built in #15, `createCodexBackend` built in #16) that implements the `AgentBackend` interface and turns a native stream into `AgentEvent`s. `AgentBackend` is the interface itself, not an implementation. Don't use "adapter" to refer to the interface.
- **"Collapsed" is two distinct things in the sidebar.** `sidebarOpen === false` hides the **whole sidebar region** (#38, app shell slice, `useAppStore`). `FileTreeItem.collapsed` describes **one directory row** whose children are folded away (`useSidebarStore.expanded`, sidebar slice). Don't call a hidden sidebar "collapsed", and don't call a folded directory "hidden".
- **"Draft" (sidebar) is not "dirty" (editor).** An `EntryDraft` is a vault entry that does not exist on disk *at all* yet — a row being named (#40). A `dirty` buffer is a note that *does* exist and has unsaved edits (`useEditorStore`). Nothing bridges them: committing a draft creates an **empty** file and opens it clean.
- **`ChatMessage`'s `role` prop is not a DOM ARIA role.** It's the design system's own `'user' | 'agent'` prop (doc/v0-spec.md §5.6 component inventory), coincidentally named the same as the HTML/ARIA `role` attribute. Biome's `lint/a11y/useValidAriaRole` flags it as a false positive at call sites — silenced there with a narrow `biome-ignore`, not a rename, to keep the prop name matching the spec's component contract.
- **Engine vs Model.** The *engine* (`AgentSource`: `claude-code`/`codex`) is which CLI is spawned; the *model* (`AgentModel`) is which LLM that CLI runs, via `--model`. The user picks a model; the engine is derived from it and is no longer a standalone setting. Don't persist an engine separately from the model.
- **"Chat store" is three distinct things.** `useChatStore` (`src/stores/chat-store.ts`) is the **in-memory** Zustand transcript for the current conversation (`items`, `turnActive`, …). The **persistence** chat store (`chats.rs` / `chatsService`, #68) is the on-disk archive under `.orbit/chats/`. `useChatHistoryStore` (`src/stores/chat-history-store.ts`, #71) is the History tab's **view-state** store (`tab`, the fetched `records`, the vim `cursorId`) — it holds *which saved chats exist and which row is highlighted*, never a transcript. They connect only through the `chat-file.ts` codec (a live transcript is serialized into a chat file; a chat file is parsed back into transcript items; the history store parses a record to hand it to `useChatStore.loadChat`). Say "the chat store" only for the in-memory transcript; call the durable side the "chat persistence store" (or name `chats.rs`/`chatsService`) and the browser side the "chat history store".
- **`--fab-accent` is a transitional alias, not a real token.** As of the Factory token & font foundation (#56), `--fab-accent`/`--fab-accent-dim` are values-only aliases of `--accent-signal`/(a derived dim shade) — kept for exactly one release so `AiFab` compiles unchanged before #58 restyles it to reference `--accent-signal` directly. Don't add a second consumer of `--fab-accent`; new code should reach for `--accent-signal`/`--accent-metric`.
